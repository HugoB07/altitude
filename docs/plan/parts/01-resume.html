Executive summary — the 12 decisions

Decisions

If you read one page, read this one. Twelve trade-offs that condition everything else, each with its short rationale and the alternative that was rejected. Detail follows in sections 3 to 7.

#TopicDecisionWhy / alternative rejected
1DatabasePostgreSQL 17 — one datastore, job queue and application cache includedExact arithmetic (numeric), window functions, JSONB, ltree, RLS, mature backup ecosystem. Rejected: SQLite (concurrency, no RLS), MongoDB (no natural multi-document transactions for a ledger).
2Accounting modelDouble-entry: every transaction is N lines summing to zero per currencyThe only structure that keeps internal transfers, fees, taxes and multi-currency coherent without double counting. Rejected: a flat transactions(amount) table — unmanageable from the second account onwards.
3Bank syncNot in v1. PSD2 connector optional in v2, off by default, credentials supplied by the operatorPSD2 does not cover PEA, assurance-vie or PER, and access requires an AISP licence. Full analysis in §7. Rejected: scraping (woob) in core — fragile, contrary to bank terms of service.
4v1 ingestionManual entry + file import (CSV, XLSX, OFX, QIF, CAMT.053) with per-bank presetsFully lawful, offline, reliable, and covers the assets PSD2 ignores. This is the foundation, not the fallback.
5FrameworkNext.js 15 App Router, React 19, RSC by defaultRoute Handlers for the versioned public API, Server Actions for internal form mutations. Explicit split in §4.4.
6ORMDrizzle ORM + drizzle-kitSQL-first, which matters when 60% of the value sits in windowed aggregates. Readable SQL migrations. Rejected: Prisma (binary engine, weaker ergonomics for raw WINDOW queries).
7Background jobspg-boss (queue inside Postgres)No extra infrastructure: one app container, one worker, one database. Rejected: BullMQ + Redis (good, but forces Redis on every self-hoster).
8AuthenticationBetter Auth (DB sessions, TOTP 2FA, passkeys, organisations)Built for self-hosting, no SaaS dependency. Its organisation plugin models the household. Rejected: Auth.js (weaker on 2FA/multi-tenancy), Clerk/WorkOS (SaaS — disqualifying here).
9Money in memoryNo float, anywhere. numeric in the database, decimal.js in TypeScript, strings at the boundariesOne cent of rounding drift destroys trust in a wealth tracker. Drizzle already returns numeric as string: we build on that.
10HierarchyPortfolio tree via ltree, with owners kept distinct from usersEnables child portfolios, holding companies, undivided estates and thematic buckets — without conflating "who owns" with "who can see".

1.1 The critical path in one sentence

A correct double-entry ledger, fed first by hand and then by file import, valued by a multi-currency pricing engine, sliced by a multi-owner portfolio tree — and only then wired to optional bank connectors. Inverting that order is the classic trap: you spend six months on aggregation, discover it does not return the PEA, and still have no product.

The trap to avoid at all costs

Bank synchronisation is the most requested feature and the least differentiating. It is expensive (regulatory exposure, connector maintenance, support load) and it covers at best 40% of a typical French user's wealth, because the wrappers holding most of the balance — PEA, assurance-vie, PER — are outside PSD2 scope. Excellent CSV import plus fast manual entry covers 100% of net worth from the first release.

1.2 v1.0 scope

In v1.0
  • Multi-type, multi-currency accounts
  • Manual transactions + import
  • Security positions, cost basis, lots
  • Quotes & FX rates
  • Net worth over time
  • Allocation + geographic globe
  • TWR & MWR (XIRR)
  • Portfolio tree + child portfolios
  • Household, roles, read-only sharing
  • Real estate + amortising loans
  • Crypto: read-only keys + on-chain
  • Complete JSON/CSV export
In v1.1 – v1.3
  • PSD2 connector (Enable Banking)
  • Budgeting & advanced categorisation
  • Goals, FIRE, Monte Carlo
  • PDF portfolio review report
  • Per-country tax modules (plugins)
  • Forward dividend calendar
  • Mobile app (PWA first)
  • Versioned public API + webhooks
Out of scope (deliberately)
  • Order placement / brokerage
  • Payment initiation (PSD2 PIS)
  • Investment advice
  • Automated tax filing
  • A project-run hosted SaaS
  • Bank scraping in core
  • Financial product marketplace
Decision — no official SaaS before v1.0

Running a public instance turns the project into an entity processing third parties' financial data: heightened GDPR obligations, liability, support, cost. A demo instance with fabricated data, reset every 24 hours, is enough to convert visitors. SaaS remains a later commercial option, one the AGPL leaves open to the project's own maintainers.
