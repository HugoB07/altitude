07

Bank synchronisation: the analysis

Decisive

The question: feasible and safe, yes or no? Short answer: technically feasible, legally constrained, and above all far less useful than it appears for this particular product. Here is the full reasoning.

7.1 The framework: who is allowed to read a bank account

In Europe, programmatic access to accounts is governed by PSD2. Three structural facts:

  • Reading account data on a user's behalf is a regulated service — an Account Information Service (AIS). Providing it requires an AISP licence from a national authority (the ACPR in France), or status as an agent of a licensed institution.
  • Technically, banks expose a dedicated interface protected by eIDAS certificates (QWAC / QSealC) issued only to licensed entities. An open-source project cannot obtain them, and could not distribute them anyway.
  • User consent is dated and time-limited. Strong customer authentication (SCA) is required on first access and renewed periodically — historically every 90 days, extended to up to 180 days by the 2022 amendment to the regulatory technical standards, depending on the bank and the aggregator.

The direct consequence: Altitude will never connect to banks directly. The only compliant route runs through a licensed aggregator, where the operator opens their own account.

7.2 What PSD2 does not cover — the point that changes everything

PSD2 applies to payment accounts. Translated into a concrete French net worth:

Asset typeReachable via PSD2Reality
Current accountYesBalance and transactions, generally 12 to 24 months of history depending on the bank.
Regulated savings (livret A, LDDS, LEP)VariesInstitution-dependent: often exposed because they are accessible online, but with no guarantee and a shorter history.
Brokerage account (CTO)NoOut of scope. At best a cash balance. No positions, no quantities, no cost basis.
PEANoOut of scope — and frequently the single largest line in a French portfolio.
Assurance-vieNoOut of scope, and insurers are under no API obligation. Some aggregators do retrieve it — by scraping, not through PSD2.
PER, PERCO, employee savingsNoOut of scope. Retrievable only by scraping or manual import.
MortgageNoA loan is not a payment account. Outstanding principal is not exposed.
Crypto, property, private equityNoEntirely outside PSD2.
The central finding

For a typical French user whose wealth is spread across a primary residence, a PEA, an assurance-vie, savings accounts and a current account, PSD2 synchronisation returns the current account and perhaps the savings accounts — typically 10 to 25% of the balance, and the least interesting part to analyse. Building the product around that brick means optimising the least important quarter first.

Three things to verify before writing any connector code
  1. The aggregator's terms: do they permit use from open-source, self-hosted software? Does "your own accounts" cover a spouse and children in the same household? Get this confirmed in writing before publishing.
  2. Consent duration and expiry behaviour: the reconnection experience must be smooth, otherwise users abandon after the second renewal.
  3. History depth actually returned. Many aggregators cap the first call at 90 days, which makes file import necessary regardless, simply to reconstruct the past.

7.5 Route C — why scraping stays out of core

Kresus showed it is possible in France through woob. That does not make it a good foundation:

The real risks
  • Bank terms of service: most forbid automation and the disclosure of credentials to a third party, including local software.
  • Liability in case of fraud: in a dispute, having entrusted credentials to a third-party tool weakens the customer's position.
  • Strong authentication: mobile-app approval on every login turns automation into an hourly notification.
  • Account lockout: unusual connection patterns trigger anti-fraud systems.
  • Maintenance cost: every bank redesign breaks a module. That is unending work for volunteer maintainers.
Altitude's position

The core contains no scraping code and the project hosts none. The Connector interface, however, is public and documented: a third party can publish an altitude-connector-woob bridge that users knowingly install.

The documentation states the trade-off plainly, without moralising: it is the user's choice on their own hardware, but it is neither supported nor recommended by the project.

7.7 Verdict and chosen architecture

Decision — bank sync: no in v1, optional in v2

v1.0 — no bank connection at all. Manual entry, file import, read-only crypto keys, on-chain addresses and IBKR Flex. This scope covers 100% of net worth, is legally unimpeachable, and depends on no third party.

v2.0 — PSD2 connector as an optional plugin, off by default, ALTITUDE_CONNECTORS=enablebanking. Reference implementation: Enable Banking, because it is the only self-service route today. The operator creates their own account and supplies their own credentials. The repository contains no keys.

Never — payment initiation, scraping in core, storage of bank credentials.

// packages/connectors/src/types.ts — the interface every connector implements
export interface Connector {
  readonly id: string;                 // 'enablebanking' | 'ibkr-flex' | 'kraken' …
  readonly capabilities: {
    accounts: boolean;
    transactions: boolean;
    positions: boolean;          // false for every PSD2 connector
    historyDays: number | 'unbounded';
    requiresUserConsent: boolean;
  };
  // Step 1: the user is redirected to their bank (credentials never reach us)
  beginLink(ctx: Ctx, params: LinkParams): Promise<{ redirectUrl: string; state: string }>;
  completeLink(ctx: Ctx, callback: unknown): Promise<ConnectionHandle>;
  // Step 2: sync — returns CANONICAL transactions, never ledger entries
  fetchAccounts(h: ConnectionHandle): Promise<RawAccount[]>;
  fetchTransactions(h: ConnectionHandle, since: Date): Promise<RawTransaction[]>;
  // Step 3: consent lifecycle
  consentExpiresAt(h: ConnectionHandle): Date | null;
  revoke(h: ConnectionHandle): Promise<void>;
}

An important architectural point: a connector produces canonical raw transactions, which then flow through exactly the same pipeline as a CSV import — normalisation, deduplication, categorisation, double-entry posting (§8.2). No code is written twice, and a sync is undoable just like an import.

7.8 Connector security

ThreatCountermeasure
Database theftTokens encrypted with AES-256-GCM using a per-record key, itself encrypted by a master key held outside the database (ALTITUDE_ENCRYPTION_KEY, a Docker secret). A stolen database without the key grants no bank access.
Internet-exposed instanceA connector's link page requires recent reauthentication and a second factor when enabled. Strict rate limiting on callback endpoints.
OAuth callback hijackingRandom state bound to the session, PKCE, strict redirect-URL checking, ten-minute validity window.
Excessive scopeOnly the AIS scope is requested. Any payment-initiation scope appearing in a response triggers an explicit refusal and an alert.
Leakage through logsMandatory redaction: IBANs, tokens, amounts and counterparty names are never written at info level. An automated test fails if an IBAN pattern appears in test logs.
Malicious connectorThird-party connectors are explicitly installed packages. The documentation says it plainly: installing a connector grants it access to your financial data.
RevocationA "Disconnect and forget everything" button deletes tokens and remote credentials, and offers to keep or purge the transactions already imported.
