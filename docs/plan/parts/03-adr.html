03

Décisions d'architecture (ADR)

Archi

Format ADR condensé : contexte → décision → conséquence. À stocker dans docs/adr/NNNN-titre.md et à faire évoluer par pull request, jamais en silence.

ADR-001 — PostgreSQL comme unique dépendance de données

Contexte
Il faut une base transactionnelle, une file de jobs, un cache, un moteur de recherche léger et des séries temporelles. La tentation est d'empiler Postgres + Redis + ClickHouse.
Décision
PostgreSQL 17 assure les quatre rôles. Extensions activées : pgcrypto, ltree, btree_gist, pg_trgm, unaccent. Redis reste possible mais optionnel.
Conséquence
Le docker-compose.yml tient en 4 services. La sauvegarde est un pg_dump unique : plus de risque d'incohérence entre deux magasins. En contrepartie, la file de jobs plafonne autour de quelques milliers de tâches/minute — très au-delà des besoins d'un foyer.
Réexamen si
Une instance dépasse ~500 utilisateurs actifs ou 50 M de lignes de cotations.

ADR-002 — Grand livre en partie double, positions dérivées

Contexte
Un virement PEA → compte courant ne doit pas apparaître comme un revenu ; un achat de titre transforme du cash en quantité ; des frais et une retenue à la source accompagnent un dividende étranger.
Décision
Une transaction porte N entries (lignes) ; la somme des lignes est nulle par devise. Les positions et soldes sont dérivés du journal, jamais saisis directement.
Conséquence
Invariant testable par propriété. Coût : chaque écriture demande plus de travail côté UI — masqué par des « recettes » (achat, vente, dividende, virement) qui génèrent les lignes.

ADR-003 — Propriétaires distincts des utilisateurs

Contexte
Un enfant de 6 ans possède un livret mais n'a pas de compte applicatif. Une SCI possède un bien mais n'est pas une personne. Un compte joint appartient à deux personnes à 50/50.
Décision
Trois notions séparées : users (qui se connecte), owners (qui possède — personne physique, morale, enfant), ownerships (quote-part datée d'un compte par un propriétaire).
Conséquence
Le patrimoine peut être découpé par propriétaire, par foyer, par utilisateur ou par portefeuille indépendamment. Toute somme d'actifs doit préciser sa base de consolidation — c'est explicite dans l'API.

ADR-004 — Connecteurs bancaires : externes, optionnels, désactivés par défaut

Contexte
L'accès aux API bancaires DSP2 exige un agrément AISP. Un projet open source ne peut pas distribuer ses propres identifiants d'agrégateur.
Décision
Interface Connector stable, implémentations distribuées séparément, activées par variable d'environnement, avec identifiants fournis par l'hébergeur. Aucune clé dans le dépôt. Analyse complète en §7.
Conséquence
Le cœur reste neutre juridiquement et testable sans réseau. La configuration d'un connecteur est une étape explicite et documentée.

ADR-005 — Server Actions pour les mutations internes, Route Handlers pour l'API

Contexte
Next.js offre deux mécanismes serveur ; mélanger les deux sans règle produit une base illisible et des trous d'autorisation.
Décision
Frontière nette : app/api/v1/** (Route Handlers) = contrat public versionné, authentifié par jeton d'API, documenté OpenAPI. Server Actions = mutations déclenchées par l'UI, authentifiées par cookie de session. Les deux appellent la même couche packages/core/services — aucune logique métier dans l'une ou l'autre.
Conséquence
La logique est testable sans HTTP. L'API publique ne dérive jamais de l'UI. Règle de revue : une Server Action de plus de 20 lignes est un bug de conception.

ADR-006 — Précision numérique : jamais de nombre flottant

Contexte
0.1 + 0.2 !== 0.3 en IEEE-754. Sur 10 000 transactions, la dérive est visible. Une quantité de crypto demande jusqu'à 18 décimales.
Décision
En base : numeric(28,10) pour les montants, numeric(38,18) pour les quantités, numeric(24,12) pour les prix et taux. En TypeScript : decimal.js. Aux frontières JSON : chaînes de caractères, jamais de number.
Conséquence
Un type Money maison encapsule montant + devise et interdit l'addition de devises différentes à la compilation. Les agrégats SQL restent exacts.

ADR-007 — Isolation multi-locataire : double barrière

Contexte
Sur une instance familiale, une requête qui oublie WHERE household_id = ? expose le patrimoine d'un autre foyer. C'est la classe de faille n°1 des applications multi-tenant.
Décision
(1) Toutes les requêtes passent par un scopedDb(ctx) qui injecte le filtre — accès direct au client Drizzle interdit par règle ESLint. (2) Row Level Security PostgreSQL en défense en profondeur, via SET LOCAL app.current_household au début de chaque transaction.
Conséquence
Une erreur applicative ne suffit pas à provoquer une fuite. Coût : les migrations doivent créer les politiques RLS, et le rôle de migration doit être distinct du rôle applicatif.

ADR-008 — Historique valorisé : instantanés quotidiens matérialisés

Contexte
Afficher 10 ans de courbe de patrimoine en rejouant le journal à chaque requête est impossible à tenir sous 200 ms.
Décision
Table daily_balances (compte × jour × devise) alimentée en incrémental par un job nocturne et invalidée depuis la date la plus ancienne touchée par une écriture. Les agrégats par portefeuille sont calculés à la volée depuis cette table.
Conséquence
Lecture rapide, reconstruction totale possible en une commande (altitude recompute --from 2015-01-01). Toute modification rétroactive déclenche un recalcul partiel — à surveiller sur les gros imports.
