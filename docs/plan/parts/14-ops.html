Self-hosting & déploiement

Ops

Critère de réussite : un utilisateur qui n'a jamais vu le projet doit avoir une instance fonctionnelle en moins de cinq minutes, avec deux commandes.

14.1 Compose de référence

# docker-compose.yml — la seule chose à télécharger
services:
  db:
    image: postgres:17-alpine
    environment: [ POSTGRES_DB=altitude, POSTGRES_USER=altitude ]
    secrets: [ db_password ]
    volumes: [ pgdata:/var/lib/postgresql/data ]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U altitude"]
      interval: 10s
    restart: unless-stopped

  app:
    image: ghcr.io/<org>/altitude:1.0            # multi-arch amd64 + arm64
    depends_on: { db: { condition: service_healthy } }
    environment:
      DATABASE_URL: postgres://altitude@db:5432/altitude
      ALTITUDE_BASE_URL: https://altitude.exemple.fr
      ALTITUDE_BASE_CURRENCY: EUR
    secrets: [ db_password, encryption_key, auth_secret ]
    volumes: [ files:/data/files ]
    healthcheck:
      test: ["CMD", "node", "healthcheck.js"]
    restart: unless-stopped

  worker:
    image: ghcr.io/<org>/altitude:1.0
    command: ["node", "worker.js"]                # même image, rôle différent
    depends_on: { db: { condition: service_healthy } }
    environment: { DATABASE_URL: "..." }
    secrets: [ db_password, encryption_key ]
    deploy: { resources: { limits: { memory: 1g } } }
    restart: unless-stopped

  caddy:                                        # TLS automatique, zéro configuration
    image: caddy:2-alpine
    ports: ["80:80", "443:443"]
    volumes: [ ./Caddyfile:/etc/caddy/Caddyfile, caddydata:/data ]
    restart: unless-stopped

volumes: { pgdata: {}, files: {}, caddydata: {} }
secrets:
  db_password:    { file: ./secrets/db_password }
  encryption_key: { file: ./secrets/encryption_key }
  auth_secret:    { file: ./secrets/auth_secret }
Décision — secrets par fichier, jamais par variable d'environnement

Les variables d'environnement fuient : docker inspect, listing de processus, journaux de plantage. Les secrets Docker sont montés en fichiers lus au démarrage. Un script ./scripts/init-secrets.sh les génère avec la bonne entropie — c'est le seul geste manuel de l'installation, et il est scripté.

14.3 Sauvegarde et restauration

altitude backup create              # pg_dump + fichiers + manifeste, chiffré
altitude backup verify <id>        # restaure dans une base jetable et compare les totaux
altitude backup restore <id>       # restauration complète
altitude export --format=json      # export lisible, indépendant du moteur
altitude doctor                    # vérifie invariants, quotes-parts, cohérence des soldes
altitude recompute --from=2015-01-01
Une sauvegarde non testée n'est pas une sauvegarde

backup verify est une commande de premier plan, pas une option cachée : elle restaure dans une base temporaire et compare le patrimoine net à une date de contrôle. La tâche planifiée l'exécute une fois par semaine et alerte en cas d'échec. C'est ce qui distingue un projet d'auto-hébergement sérieux d'un projet amateur.

14.4 Mises à jour

  • Migrations exécutées au démarrage par le conteneur app, sous un verrou consultatif Postgres — deux répliques ne migrent jamais en parallèle.
  • Migrations en avant seulement, écrites pour être compatibles avec la version précédente (ajout de colonne nullable, remplissage, puis contrainte dans une version ultérieure). Pas de retour arrière automatique : une sauvegarde vérifiée est la stratégie de repli.
  • Versionnage sémantique. Toute rupture est annoncée une version mineure à l'avance et listée dans UPGRADING.md.
  • Étiquettes d'images : 1.2.3, 1.2, 1, latest. La documentation recommande d'épingler la version mineure.
  • Sauvegarde automatique déclenchée avant toute migration destructive.

16.1 Licence

Décision — AGPL-3.0-or-later

L'AGPL impose à quiconque exploite une version modifiée en tant que service réseau d'en publier le code. C'est exactement la protection nécessaire face à un concurrent commercial qui voudrait reprendre le travail communautaire sans rien rendre. Précédents directs : Firefly III, Ghostfolio, Sure. Contrainte assumée : certaines entreprises s'interdisent l'AGPL en interne — c'est un coût d'adoption accepté au profit de la pérennité du commun.

Contributions sous DCO (Signed-off-by) plutôt que CLA : moins de friction, et pas de transfert de droits à une entité unique. Si une double licence commerciale devient souhaitable plus tard, elle exigera un CLA — mieux vaut alors trancher tôt.

16.3 Amorcer une communauté

  • Démo publique avec données factices, réinitialisée toutes les 24 h. C'est le premier convertisseur : personne n'installe un logiciel de patrimoine sans l'avoir vu tourner.
  • 15 tickets « bonne première contribution » préparés avant l'annonce, majoritairement des presets d'import et des jeux d'exposition d'ETF — utiles, cadrés, sans risque.
  • Feuille de route publique (GitHub Projects), discussions ouvertes pour les demandes de fonctionnalités.
  • Annonce quand la démo tient debout : r/selfhosted, r/vosfinances, Hacker News, Awesome-Selfhosted, forums d'auto-hébergement francophones. Une seule chance de première impression : ne pas annoncer avant que l'import et le dashboard soient solides.
  • Bilingue dès le départ : documentation FR et EN. Le marché de l'auto-hébergement est anglophone, le besoin patrimonial visé est francophone.
  • Financement : GitHub Sponsors / Liberapay pour couvrir démo et domaine. Pas de promesse de version « pro » tant que la v1.0 n'est pas livrée.
