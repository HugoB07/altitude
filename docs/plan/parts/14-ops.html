14.1 Reference compose file

# docker-compose.yml — the only thing to download
services:
  db:
    image: postgres:17-alpine
    environment: [ POSTGRES_DB=altitude, POSTGRES_USER=altitude ]
    secrets: [ db_password ]
    volumes: [ pgdata:/var/lib/postgresql/data ]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U altitude"]
      interval: 10s
    restart: unless-stopped

  app:
    image: ghcr.io/<org>/altitude:1.0            # multi-arch amd64 + arm64
    depends_on: { db: { condition: service_healthy } }
    environment:
      DATABASE_URL: postgres://altitude@db:5432/altitude
      ALTITUDE_BASE_URL: https://altitude.example.com
      ALTITUDE_BASE_CURRENCY: EUR
    secrets: [ db_password, encryption_key, auth_secret ]
    volumes: [ files:/data/files ]
    healthcheck:
      test: ["CMD", "node", "healthcheck.js"]
    restart: unless-stopped

  worker:
    image: ghcr.io/<org>/altitude:1.0
    command: ["node", "worker.js"]                # same image, different role
    depends_on: { db: { condition: service_healthy } }
    environment: { DATABASE_URL: "..." }
    secrets: [ db_password, encryption_key ]
    deploy: { resources: { limits: { memory: 1g } } }
    restart: unless-stopped

  caddy:                                        # automatic TLS, zero configuration
    image: caddy:2-alpine
    ports: ["80:80", "443:443"]
    volumes: [ ./Caddyfile:/etc/caddy/Caddyfile, caddydata:/data ]
    restart: unless-stopped

volumes: { pgdata: {}, files: {}, caddydata: {} }
secrets:
  db_password:    { file: ./secrets/db_password }
  encryption_key: { file: ./secrets/encryption_key }
  auth_secret:    { file: ./secrets/auth_secret }
Decision — file-based secrets, never environment variables

Environment variables leak: docker inspect, process listings, crash logs. Docker secrets are mounted as files and read at startup. A ./scripts/init-secrets.sh script generates them with proper entropy — the single manual step of the installation, and it is scripted.

14.3 Backup and restore

altitude backup create              # pg_dump + files + manifest, encrypted
altitude backup verify <id>        # restores into a throwaway database and compares totals
altitude backup restore <id>       # full restore
altitude export --format=json      # readable export, engine-independent
altitude doctor                    # checks invariants, ownership shares, balance coherence
altitude recompute --from=2015-01-01
An untested backup is not a backup

backup verify is a first-class command, not a hidden flag: it restores into a temporary database and compares net worth at a control date. The scheduled task runs it weekly and alerts on failure. This is what separates a serious self-hosting project from an amateur one.

14.4 Upgrades

  • Migrations run at startup from the app container, under a Postgres advisory lock — two replicas never migrate concurrently.
  • Forward-only migrations, written to remain compatible with the previous version (add a nullable column, backfill, then add the constraint in a later release). No automatic rollback: a verified backup is the fallback strategy.
  • Semantic versioning. Any breaking change is announced one minor version ahead and listed in UPGRADING.md.
  • Image tags: 1.2.3, 1.2, 1, latest. Documentation recommends pinning the minor version.
  • An automatic backup is triggered before any destructive migration.

14.5 Sizing

ProfileRAMCPUNotes
Household, < 20k transactions1 GB1 vCPURuns on a Raspberry Pi 4 or a NAS. Native arm64 image.
Household, > 10 years of history2 GB2 vCPUThe main load is snapshot recomputation.
Small group, 10–50 households4 GB4 vCPUSplit worker and app across two hosts, add a read replica if needed.

Indicative volumes: 100,000 transactions ≈ 250 MB including indexes; quotes dominate storage (10 years × 500 instruments ≈ 1.8M rows ≈ 200 MB) — hence the partitioning and the BRIN index.

16.1 Licence

Decision — AGPL-3.0-or-later

The AGPL requires anyone operating a modified version as a network service to publish its source. That is exactly the protection needed against a commercial competitor rebuilding community work without giving anything back. Direct precedents: Firefly III, Ghostfolio, Sure. Accepted cost: some companies ban the AGPL internally — an adoption price paid for the durability of the commons.

Contributions under DCO (Signed-off-by) rather than a CLA: less friction, and no transfer of rights to a single entity. If commercial dual licensing later becomes desirable it will require a CLA — better to settle that question early.

16.3 Bootstrapping a community

  • Public demo with fabricated data, reset every 24 hours. It is the primary converter: nobody installs a wealth tracker without seeing it run.
  • Fifteen "good first issue" tickets prepared before announcing, mostly import presets and ETF exposure datasets — useful, well-scoped, low-risk.
  • Public roadmap (GitHub Projects), with open discussions for feature requests.
  • Announcement once the demo stands up: r/selfhosted, personal-finance communities, Hacker News, Awesome-Selfhosted, self-hosting forums. You get one first impression: do not announce before import and the dashboard are solid.
  • Bilingual from day one: English and French documentation. The self-hosting market is anglophone; the wealth-tracking need targeted here is francophone.
  • Funding: GitHub Sponsors / Liberapay to cover the demo and the domain. No promise of a "pro" edition until v1.0 ships.
