Semaine 1 : checklist concrète

Projet

De quoi démarrer lundi matin. Rien ici n'est spéculatif : chaque ligne est exécutable.

Jour 1 — squelette

pnpm dlx create-turbo@latest altitude
cd altitude && git init && git commit -m "chore: init"
pnpm dlx create-next-app@latest apps/web --ts --tailwind --app --src-dir --import-alias "@/*"
pnpm add -w -D typescript vitest @vitest/coverage-v8 eslint prettier dependency-cruiser
pnpm add -F @altitude/db drizzle-orm postgres && pnpm add -F @altitude/db -D drizzle-kit
pnpm add -F @altitude/shared decimal.js zod
mkdir -p docs/adr packages/{db,core,shared,ui,importers} apps/worker docker
  • Écrire docs/adr/0001-postgres.md et 0002-partie-double.md — figer les deux décisions les plus structurantes avant d'écrire du code.
  • Créer docker/docker-compose.dev.yml avec le seul service db (Postgres 17).
  • Configurer tsconfig strict à la racine, hérité par tous les paquets.

Jour 2 — le domaine avant l'interface

  • Dans packages/shared : types Money, Currency, Decimal, types de marque pour les identifiants.
  • Dans packages/core : Ledger.createTransaction() avec validation de l'équilibre, en mémoire, sans base de données.
  • Écrire les tests de propriétés fast-check maintenant : ils définissent le modèle.
  • Vérifier que packages/core n'a aucune dépendance à React ou Next — règle dependency-cruiser en place dès le premier jour.

Jour 3 — schéma et migrations

  • Schéma Drizzle : households, users, owners, portfolios, accounts, transactions, entries.
  • Migration SQL manuelle pour ce que Drizzle ne génère pas : extensions, ltree, déclencheur d'équilibre, politiques RLS.
  • Seed de démonstration : un foyer, deux propriétaires, quatre comptes, cinquante transactions.
  • Premier test Testcontainers : la migration s'applique, le déclencheur rejette bien une transaction déséquilibrée.

Jour 4 — authentification et coquille

  • Better Auth avec adaptateur Drizzle, courriel + mot de passe, session en base.
  • getContext() serveur → { user, household, role } ; scopedDb(ctx) qui pose SET LOCAL.
  • Coquille applicative : barre latérale, sélecteur de portefeuille, thème clair/sombre, shadcn installé.
  • Assistant de première installation : création du foyer, devise de référence, premier compte.

Jour 5 — la boucle qui prouve tout

  • Server Action createTransaction → service core → base.
  • Formulaire d'ajout rapide (dépôt, retrait, virement) et table listant les transactions.
  • Calcul du solde par compte en SQL, affiché sur le dashboard.
  • Objectif de fin de semaine : saisir un dépôt de 1 000 €, un virement de 300 € vers un second compte, et voir un patrimoine net de 1 000 € — pas 1 300 €. Si ce chiffre est juste, le modèle est bon et tout le reste est de l'assemblage.
Le premier vrai jalon

Fin de semaine 3 : importer son propre export bancaire et voir sa vraie courbe de patrimoine. À partir de ce moment, le projet devient son propre utilisateur — c'est le meilleur moteur de motivation et le meilleur détecteur de défauts d'ergonomie.

Dette technique du schémaMoyenneÉlevéLe temps investi en §5 est la mitigation. Migrations en avant seulement, testées sur des données réalistes.
Le seul risque vraiment fatal

Ce n'est ni la technique, ni le juridique : c'est de construire pendant huit mois sans jamais livrer. Un outil de patrimoine est un projet à la surface d'attaque fonctionnelle infinie — il y aura toujours une classe d'actifs de plus, un preset de plus, un ratio de plus. La discipline de sortir une v1.0 étroite mais irréprochable est la compétence critique de ce projet, plus que n'importe quel choix de stack.

20.2 Glossaire

TermeDéfinition
AISPAccount Information Service Provider — prestataire agréé pour lire les données de comptes de paiement au titre de la DSP2.
SCAStrong Customer Authentication — authentification forte, requise au premier accès puis périodiquement.
CAMT.053Relevé bancaire structuré au format XML ISO 20022. Le format d'export le plus riche disponible.
TWRTime-Weighted Return — performance neutralisant l'effet des apports et retraits. Comparable à un indice.
TRI / MWRTaux de rendement interne — performance tenant compte du calendrier des flux. Répond à « combien mon argent m'a rapporté ».
PMP / CUMPPrix moyen pondéré — méthode de prix de revient utilisée en France pour les titres.
TransparisationDécomposition d'un fonds en ses expositions sous-jacentes (pays, secteurs) pour mesurer la vraie diversification.
Partie doublePrincipe comptable où chaque opération est enregistrée en au moins deux écritures dont la somme est nulle.
RLSRow Level Security — filtrage des lignes appliqué par PostgreSQL lui-même, indépendamment de l'application.
ltreeType PostgreSQL représentant un chemin hiérarchique, permettant d'interroger un sous-arbre en une opération.

Prochaine étape

Ce document fixe le cadre ; il n'a pas vocation à rester figé. Les trois points à trancher avant d'écrire la première ligne : (1) confirmer AGPL-3.0 plutôt que MIT — c'est irréversible en pratique une fois les contributions arrivées ; (2) valider le périmètre v1.0 de la §1.2 en acceptant explicitement ce qui en est exclu ; (3) décider si la cible est d'abord francophone (enveloppes FR, presets FR) ou d'emblée européenne — cela change l'ordre des presets et la priorité du module fiscal, pas l'architecture.
