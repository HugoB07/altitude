Week 1: concrete checklist

Project

Enough to start on Monday morning. Nothing here is speculative: every line is executable.

Day 1 — skeleton

pnpm dlx create-turbo@latest altitude
cd altitude && git init && git commit -m "chore: init"
pnpm dlx create-next-app@latest apps/web --ts --tailwind --app --src-dir --import-alias "@/*"
pnpm add -w -D typescript vitest @vitest/coverage-v8 eslint prettier dependency-cruiser
pnpm add -F @altitude/db drizzle-orm postgres && pnpm add -F @altitude/db -D drizzle-kit
pnpm add -F @altitude/shared decimal.js zod
mkdir -p docs/adr packages/{db,core,shared,ui,importers} apps/worker docker
  • Write docs/adr/0001-postgres.md and 0002-double-entry.md — pin the two most structural decisions before writing any code.
  • Create docker/docker-compose.dev.yml with a single db service (Postgres 17).
  • Configure a strict root tsconfig, inherited by every package.

Day 2 — domain before interface

  • In packages/shared: Money, Currency and Decimal types, plus branded id types.
  • In packages/core: Ledger.createTransaction() with balance validation, in memory, with no database.
  • Write the fast-check property tests now: they define the model.
  • Verify packages/core has no dependency on React or Next — the dependency-cruiser rule goes in on day one.

Day 3 — schema and migrations

  • Drizzle schema: households, users, owners, portfolios, accounts, transactions, entries.
  • A hand-written SQL migration for what Drizzle cannot generate: extensions, ltree, the balance trigger, the RLS policies.
  • Demo seed: one household, two owners, four accounts, fifty transactions.
  • First Testcontainers test: the migration applies, and the trigger does reject an unbalanced transaction.

Day 4 — authentication and shell

  • Better Auth with the Drizzle adapter, email and password, sessions in the database.
  • Server-side getContext() → { user, household, role }; scopedDb(ctx) issuing the SET LOCAL statements.
  • Application shell: sidebar, portfolio picker, light/dark theme, shadcn installed.
  • First-run wizard: create the household, pick a base currency, add the first account.

Day 5 — the loop that proves everything

  • A createTransaction Server Action → core service → database.
  • Quick-add form (deposit, withdrawal, transfer) and a table listing transactions.
  • Per-account balance computed in SQL and shown on the dashboard.
  • End-of-week goal: record a €1,000 deposit and a €300 transfer to a second account, and see a net worth of €1,000 — not €1,300. If that number is right, the model is sound and everything else is assembly.
The first real milestone

End of week 3: import your own bank export and see your real net worth curve. From that moment the project becomes its own user — the best motivation engine and the best detector of usability flaws there is.

Risks & mitigations

Project
RiskProb.ImpactMitigation
Scope creep
risk number one, by a wide margin		Very highFatalv1.0 scope frozen (§1.2). Every new idea goes to the roadmap board, not the working branch. Each phase's exit criterion is written before the phase starts.
Maintainer burnoutHighFatalBe your own user from week 3. Ship something usable in six weeks rather than a masterpiece in twelve months. Decline out-of-scope requests without guilt.
A quote provider shuts down or starts chargingHighMediumMulti-provider interface with fallback from phase 3. Prices can always be entered manually. FX comes from the ECB, which will not shut down.
An aggregator changes its termsHighLowPrecisely why synchronisation is optional and outside the core. The product works without it.
Silent calculation bugMediumFatalProperty tests, oracle scenarios and altitude doctor. Every aggregate displays its method and as-of date.
Cross-household isolation flawLowFatalTwo barriers (ADR-007) and systematic cross-tenant access tests on every entry point.
User data lossLowFatalWeekly verified backups, immutable ledger, import rollback, always-available export.
No adoptionMediumHighPublic demo before announcing, screenshot at the top of the README, five-minute install, bilingual documentation.
Users lost during onboardingHighHighGuided wizard, demo data explorable without entering anything, import as the second screen rather than buried in settings.
Confusion with financial adviceMediumMediumNo investment recommendations. Projections are simulations, labelled as such. Tax modules produce filing-assistance figures, never advice.
Schema technical debtMediumHighThe time invested in §5 is the mitigation. Forward-only migrations, tested against realistic data.
The only genuinely fatal risk

It is neither technical nor legal: it is building for eight months and never shipping. A wealth tracker has an infinite functional surface — there will always be one more asset class, one more preset, one more ratio. The discipline to ship a narrow but flawless v1.0 is this project's critical skill, more than any stack choice.

20.2 Glossary

TermDefinition
AISPAccount Information Service Provider — an entity licensed under PSD2 to read payment-account data.
SCAStrong Customer Authentication — required on first access and periodically thereafter.
CAMT.053Structured bank statement in ISO 20022 XML. The richest export format available.
TWRTime-Weighted Return — return that neutralises the effect of deposits and withdrawals. Comparable to an index.
MWR / IRRMoney-Weighted Return — return that accounts for cash-flow timing. Answers "what did my money earn me".
PEAPlan d'Épargne en Actions — French tax-advantaged equity account; gains are taxed only on withdrawal, with a five-year rule.
Assurance-vieFrench life-insurance investment wrapper; partial withdrawals are split pro rata between capital and gains.
PERPlan d'Épargne Retraite — French retirement savings plan with deductible contributions.
Look-throughDecomposing a fund into its underlying exposures (countries, sectors) to measure genuine diversification.
Double-entryThe accounting principle whereby every operation is recorded as at least two entries that sum to zero.
RLSRow Level Security — row filtering enforced by PostgreSQL itself, independently of the application.
ltreeA PostgreSQL type representing a hierarchical path, allowing a whole subtree to be queried in one operation.
